# 사내 LAN용 SQLite와 백업

여행사에서 지정한 Windows PC 한 대가 DB와 API를 실행합니다. 같은 공유기·사내망의 직원은 브라우저로 접속해 동일한 예약을 조회·수정합니다. 실제 배포·이전·복구 절차는 [Windows 실행 안내](ENTRIP_RUN_GUIDE.md)에 있습니다.

## 저장하는 정보

| 구분 | 구현 |
| --- | --- |
| 업무 데이터 | 기존 35개 Prisma 모델을 SQLite에 유지합니다. 구형 예약 내부 ID와 수배·정산의 외래키를 보존하고, 새 업무 데이터에 UUID를 부여합니다. |
| 여행사·기기 | `EntripSyncAgency`가 회사 코드와 여행사 UUID를 연결합니다. `EntripSyncDevice`가 설치 기기 ID, DB ID, 현재 변경 스트림 ID를 관리합니다. |
| 업무 행 | `EntripSyncEntity`에서 원래 테이블·ID로 동기화 UUID, 현재 차수, 마지막 변경 ID와 수정·삭제 시각을 찾을 수 있습니다. 기존 CUID로 조회한 예약도 계속 열립니다. |
| 변경 이력 | 예약·수배·정산·직원·대화 등 여행사 소유 25개 테이블의 쓰기와 함께 `EntripSyncChange`에 변경을 기록합니다. 여행사별 순번을 조회할 수 있고, 직전 변경 ID와 차수로 변경의 출발점을 판별할 수 있습니다. 일시 접속·외부 캐시와 인증 비밀번호 해시는 동기화 본문에서 제외합니다. |
| 충돌·복구 | 두 직원이 같은 예약 버전을 편집하면 먼저 저장한 값이 유지되고 오래된 버전에는 HTTP 412가 반환됩니다. 복구 후에는 변경 스트림 ID가 바뀝니다. 별도 PC 간 전송, 자동 발견, 오프라인 동기화 및 충돌 병합은 후속 개발 범위입니다. |

이전 PostgreSQL에 외부 여행사 예약을 참조하는 구형 항공편이 있을 수 있습니다. 이전 도구는 원본을 보존하고, 동기화 이력에서는 해당 행의 본문과 외부 여행사 연결을 가립니다. 올바른 자사 예약으로 연결하면 그 시점의 정상 스냅샷이 기록됩니다.

## 이전과 백업의 검증

- 직전 인쇄 검증에 사용한 PostgreSQL의 업무 데이터 321행을 이전했습니다. 35개 모델을 SQLite용 Prisma로 다시 조회해 원본과 대조했습니다. 예약 130건, 메시지 118건, 직원 14명, 예약 이력 36건을 포함합니다. 부가 열과 구형 데이터의 보관 기록 457행도 이전했습니다.
- 별도 데이터로 밀리초 단위 일시, 비밀번호 해시, JSON의 null과 SQL NULL, 좌석 배열, 소수점 판매금, 환율 9.175, 연결된 수배·정산을 대조했습니다. 원본 숫자를 SQLite에서 정확히 보존할 수 없는 경우에는 반올림 없이 이전을 중단합니다. 기존 PostgreSQL 볼륨은 남아 있습니다.
- 이력 트리거를 켠 SQLite에서 API 테스트 93개를 통과했습니다. 등록된 이력 10,001건을 가진 별도 DB에서는 초기화를 반복해도 첫 등록 이력이 중복되지 않았습니다.
- 백업·복구 11개와 변경 이력 5개 검증을 통과했습니다. 예약 삭제 전 백업을 복구해 원래 UUID·이력 순번을 재확인했고, 운영 중 복원 차단, 보존 기한, 한국시간 예약 시각, 전원 차단 후 복원 재개도 검사했습니다.
- 압축 해제한 배포본에서 두 브라우저의 직원 로그인·예약 공유·실시간 대화를 확인했습니다. 계정명을 바꾸고 백업으로 복구한 뒤에는 원래 계정 ID와 이름이 돌아왔고, SQLite 전체 무결성·외래키 검사도 통과했습니다.
